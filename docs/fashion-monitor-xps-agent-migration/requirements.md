# Requirements: Migrate fashion-monitor deploy target from desktop-agent to xps-agent

## Problem statement
fashion-monitor's deployed copy — SQLite database, dashboard, mcp-server, grafana, ntfy, and a hand-installed (never-committed) scraper-health watchdog timer — currently lives on desktop-agent, per the Makefile's `DEPLOY_HOST`/`DEPLOY_USER` and the repo's CLAUDE.md. Poshmark scraping through this stack hard-depends on a stealth sidecar reachable only via `network_mode: container:gluetun-scraper`, and that gateway now runs on xps-agent instead of (or in addition to) desktop-agent, as separate already-completed home-infra work. Preston, the sole operator, needs the fashion-monitor deploy moved to xps-agent so its Poshmark scraping path has a working stealth dependency again, without losing the live database, without a window where both hosts are simultaneously acting as the live deploy, and without accidentally triggering a real scrape against live marketplaces as a side effect of verifying the move worked.

## Users / stakeholders
- Preston — sole operator; runs `make deploy`, reviews dashboard/grafana, receives ntfy alerts, approves decommissioning desktop-agent's copy.
- AI coding agents operating this repo — consult `CLAUDE.md` and the `fashion-monitor-run-and-operate` skill doc to know where the deploy lives; must not be misdirected to a stale host.
- desktop-agent — current deploy host; source of the live DB and the hand-installed timer/service being retired.
- xps-agent — new deploy host; already hosts the healthy gluetun-scraper/stealth-sidecar stack this migration depends on.

## Functional requirements
1. The system shall repoint the Makefile's `DEPLOY_HOST` (and, if the deployed account differs from desktop-agent's dedicated `fashionmonitor` service user, `DEPLOY_USER`) so that `make sync`, `make push`, and `make deploy` operate against xps-agent instead of desktop-agent.
2. The system shall leave `docker-compose.yml`'s `network_mode: "container:gluetun-scraper"` on `scraper`/`poshmark` unchanged, since xps-agent's gluetun-scraper container satisfies this dependency under the same container name.
3. The system shall confirm xps-agent's architecture is `x86_64` (e.g. `ssh xps-agent "uname -m"`) before build/deploy proceeds, since Playwright Chromium requires it per the `fashion-monitor-run-and-operate` skill doc's existing pre-flight note, which has never previously been checked for xps-agent specifically.
4. The system shall create a dedicated `fashionmonitor` service user on xps-agent (created idempotently, mirroring the existing scraper-egress account-creation pattern), owning `/opt/docker/fashion-monitor` and its contents, before `make sync`/`make push` are run against xps-agent.
5. The system shall stop desktop-agent's `fashion-monitor-scraper-health.timer` before the DB backup/copy step (FR6) begins, so it cannot write to the database mid-copy; the timer shall not be disabled or uninstalled at this point — that happens only at decommission (FR17).
6. The system shall copy `fashion_monitor.db`, `fashion_monitor.db-shm`, and `fashion_monitor.db-wal` from desktop-agent to xps-agent's `$(DEPLOY_PATH)/data/` as a single migration, with all three files copied from a consistent point in time (no writer active against the DB during the copy).
7. The system shall verify the migrated database on xps-agent is byte-identical (checksum match) to the source files captured immediately before the copy, or, if the WAL is checkpointed as part of the move, shall verify equivalent row counts in the DB's tables between source and destination.
8. The system shall ensure the migrated database files are owned by `fashionmonitor:fashionmonitor` with mode `600` on xps-agent, matching desktop-agent's existing permission model.
9. The system shall verify WRITE access (not merely read access) to the migrated database before cutover completes, via a safe, non-scrape write probe (e.g. an `INSERT` into a low-risk/throwaway table followed by a `ROLLBACK` within a single transaction, or equivalent) proving the app's runtime UID can write to the DB, without leaving any permanent change or triggering app logic.
10. The system shall NOT attempt to migrate a `data/poshmark-profile` directory, since none exists on desktop-agent as of this migration (no Poshmark cookies have been persisted yet); the migrated xps-agent instance shall be left able to create that directory fresh the first time Poshmark scraping is opted into.
11. The system shall create `fashion-monitor-scraper-health.timer` and `fashion-monitor-scraper-health.service` as new files tracked in this repository's git history (they currently exist only as hand-installed, uncommitted units on desktop-agent).
12. The system shall install the committed `fashion-monitor-scraper-health.timer`/`.service` on xps-agent such that `systemctl list-timers` on xps-agent shows the timer active and its `.service` invokes `docker compose --profile tools run --rm scraper-health` against the xps-agent deploy path.
13. The system shall bring up xps-agent's long-lived services (`dashboard`, `mcp-server`, `grafana`, `ntfy`) via a docker compose invocation scoped to those four named services only — never a bare `docker compose up -d` or `make deploy` — during the cutover/verification window, since `scraper`/`poshmark`/`score` lack a `profiles:` gate and would start as a side effect.
14. The system shall update the `fashion-monitor-run-and-operate` skill doc's deploy-host references (desktop-agent, `desktop`, and any desktop-specific paths/notes) to reflect xps-agent as the deploy target, and shall ADD new documentation for the `fashion-monitor-scraper-health.timer`/`.service` watchdog (a new docker-compose service-map row plus a new subsection covering its install command and how to verify it) now that they are committed and installed. The system shall NOT alter the doc's existing sentence describing `scraper`/`poshmark`/`score`'s own scrape-execution scheduling (currently "Not yet actually installed") — that sentence is about those services' own scheduling, not the scraper-health watchdog, remains accurate, and must stay unchanged and textually distinct from the new watchdog documentation.
15. The system shall verify the xps-agent deploy is functional before any decommissioning step touches desktop-agent's copy — verification and decommissioning shall not overlap in time, and decommissioning shall not begin until verification has passed.
16. The system shall perform verification using only non-scrape-triggering checks: container `Up` state (`docker compose ps`) for `dashboard`, `mcp-server`, `grafana`, and `ntfy`; a direct DB read (e.g. a row-count or schema query against the migrated `fashion_monitor.db`) confirming connectivity; a write-access probe (FR9); an HTTP reachability check against the `dashboard`'s, `grafana`'s, and `ntfy`'s listening ports; and, for `mcp-server` (SSE-based, not trivially HTTP-probed), an `Up`-state check plus an error-free tail of its container logs is sufficient — the system shall NOT invoke `scraper`, `poshmark`, `score`, or any `pnpm run verify:scrapers`/`test:live` command as part of this migration's verification step.
17. The system shall, only after verification passes AND xps-agent's replacement `fashion-monitor-scraper-health.timer`/`.service` (FR12) is confirmed installed and active, stop and remove desktop-agent's fashion-monitor containers (`mcp-server`, `dashboard`, `grafana`, `ntfy` — the currently-running long-lived services) and uninstall the hand-installed `fashion-monitor-scraper-health.timer`/`.service` from desktop-agent.
18. The system shall recreate `$(DEPLOY_PATH)/data/.env` on xps-agent (containing `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `ENCRYPTION_KEY`, and the other secrets `.env.example` documents) before first `make deploy` against xps-agent, since `make sync` never syncs `.env` and it is not part of the DB migration.
19. The system shall confirm gluetun-scraper is running and healthy on xps-agent before bringing up `scraper`/`poshmark` there (their `network_mode: container:gluetun-scraper` dependency cannot start without it, and `depends_on` cannot express this cross-compose-project dependency).
20. The system shall retain desktop-agent's original database files (`fashion_monitor.db*`) untouched for at least 24-48 hours post-decommission before they are considered safe to delete, serving as the only rollback copy during that window.
21. The system shall add `profiles: ["scrape"]` to the `scraper`, `poshmark`, and `score` service definitions in `docker-compose.yml`, so that no future bare `docker compose up -d`/`make deploy` (beyond just this migration's cutover) can ever start them as a side effect.

## Non-functional requirements
- Data integrity: the migrated DB must be an exact, non-corrupted copy of desktop-agent's live data at the moment of cutover (checksum or row-count verified per FR7) — no silent partial-WAL copy.
- No live-marketplace side effects: verification steps must be provably scrape-free (no new rows in `seen_listings`, no scraper/poshmark container invocation, no new ntfy alert dispatched during the verification window).
- No secrets in git: `.env`, `data/`, and DB files remain gitignored throughout; only the timer/service unit files and doc updates are committed.
- No dual-live window: at no point should both desktop-agent and xps-agent be simultaneously treated as the authoritative deploy — cutover is a single ordered handoff, not a period of dual operation. "Authoritative deploy" specifically means the **dashboard** (the source of truth for what Preston sees/interacts with); a brief `grafana`/`ntfy` overlap between hosts during the verification window (before decommission) is acceptable and does not violate this NFR, since neither performs writes or alert-worthy actions during that window (`score` is not running).
- Never expose secret values: `.env` variable VALUES must never be printed or dumped (e.g. via `cat .env`) during any debugging of this migration; checking variable NAMES/presence (e.g. `grep -o '^[A-Z_]*=' .env`) is fine.

## Constraints
- Deploy pipeline is Makefile-driven (`make sync`/`push`/`deploy`) and unchanged in mechanism — only `DEPLOY_HOST`/`DEPLOY_USER` (and `DEPLOY_PATH` if it must differ) move.
- `make sync` never syncs `.env` or `data/` (existing, deliberate behavior) — secrets and the DB must be handled outside `make sync`.
- Poshmark/scraper containers hard-depend on xps-agent's gluetun-scraper container via `network_mode: container:gluetun-scraper`; that dependency is already satisfied per the feature's stated context and must not be re-litigated by this migration.
- desktop-agent must remain reachable and operational (its currently-running `mcp-server`, `dashboard`, `grafana`, `ntfy` containers) until verification of the xps-agent copy has passed — no premature teardown.
- The account fashion-monitor's containers run under on xps-agent is `fashionmonitor` (matching desktop-agent's dedicated service user), created per FR4.
- Repo convention (`CLAUDE.md`) already prohibits casual live-scrape runs from a Mac clone; this migration extends that same caution to a freshly-redeployed xps-agent instance's initial verification.

## Out of scope
- Deploying or reconfiguring gluetun-scraper or the stealth-sidecar on xps-agent — already complete, separate home-infra work.
- Fixing the scraper-health timer's currently-failing alert state (no scrape has ever succeeded through it). Committing and installing the timer/service does not resolve this; resolution requires a real, deliberately opt-in scrape run, which this migration's verification step explicitly excludes.
- Registering the new timer/service with home-infra's config-drift-monitor manifest, if such tracking exists for xps-agent-hosted units.
- Running `pnpm run verify:scrapers` / `pnpm run test:live` or any other live-marketplace scrape as part of this migration.
- Updating fashion-monitor's CLAUDE.md beyond its one stale deploy-host bullet — the rest of the file's content stays untouched.
- Wiring the dashboard behind a TLS-terminating proxy (e.g. Caddy) on xps-agent — the plain-HTTP host-port exposure pattern carries over unchanged.
- Any change to `docker-compose.yml` service definitions beyond what FR2 (network_mode unchanged) and FR21 (`profiles: ["scrape"]` added to `scraper`/`poshmark`/`score`) already account for.
- Creating or backfilling a `data/poshmark-profile` directory — none exists to migrate (FR10).

## Acceptance criteria
1. `make -n deploy` (or equivalent dry inspection of the Makefile) shows `DEPLOY_HOST` resolving to xps-agent, not desktop-agent.
2. `make sync` and `make push` run against xps-agent each complete with exit code 0, followed by a scoped `docker compose up -d dashboard mcp-server grafana ntfy` (FR13) completing with exit code 0; `docker compose ps` on xps-agent then shows `dashboard`, `mcp-server`, `grafana`, and `ntfy` each in an `Up` state.
3. A checksum (or row-count) comparison between the desktop-agent source DB files (captured pre-copy) and the xps-agent-hosted `fashion_monitor.db` matches exactly.
4. An HTTP request to the xps-agent dashboard's listening port returns a 2xx response, without any scraper/poshmark/score container having run during the verification session.
5. HTTP reachability checks against `grafana`'s and `ntfy`'s listening ports each return a 2xx response; `mcp-server` (SSE-based, not trivially HTTP-probed) is instead confirmed via `docker compose ps` showing an `Up` state plus an error-free tail of its container logs.
6. A direct query against the migrated `fashion_monitor.db` on xps-agent (e.g. `seen_listings` row count) succeeds and matches the pre-migration source count.
7. A safe write probe (e.g. an `INSERT` into a throwaway/low-risk table followed by a `ROLLBACK` within a single transaction) against the migrated `fashion_monitor.db` on xps-agent succeeds under the app's runtime UID, confirming write access, without leaving any permanent change or triggering app logic.
8. `git log -- fashion-monitor-scraper-health.timer fashion-monitor-scraper-health.service` (or their final committed paths) shows both files tracked in this repository.
9. `systemctl list-timers` on xps-agent lists `fashion-monitor-scraper-health.timer` as active, pointing at a `.service` whose `ExecStart` invokes `docker compose --profile tools run --rm scraper-health` under the xps-agent deploy path.
10. A presence check (variable NAMES only, never values) against xps-agent's recreated `.env` confirms `TELEGRAM_BOT_TOKEN`, `ENCRYPTION_KEY`, and `GRAFANA_ADMIN_PASSWORD` are all present before `dashboard`/`grafana` are brought up.
11. `grep -i "desktop"` against `.claude/skills/fashion-monitor-run-and-operate/SKILL.md` returns no remaining references to desktop-agent as the live deploy target (historical/migration-note mentions excepted).
12. `.claude/skills/fashion-monitor-run-and-operate/SKILL.md` contains a new docker-compose service-map row for `scraper-health` and a new subsection documenting the installed watchdog timer/service (FR14), while the existing sentence describing `scraper`/`poshmark`/`score`'s own scrape-execution scheduling remains textually unchanged.
13. desktop-agent's fashion-monitor containers (`mcp-server`, `dashboard`, `grafana`, `ntfy`) and its hand-installed scraper-health timer/service are stopped/removed only after criteria 2–7 and criterion 9 (xps-agent's replacement timer/service confirmed active) have passed, verifiable by a timestamp ordering in the operator's change log or shell history.
14. No new row appears in `seen_listings` and no new ntfy alert is dispatched as a result of any step performed to satisfy criteria 1–13.
